## 1. 这套系统整体是什么

### 1.1 一句话

**用户在网页上配置好"讲解方案"（哪些点、每点说什么话），机器人按顺序自己导航到每个点，到了就开口把讲解词念出来，全部念完回充电桩。**

### 1.2 全景图

```
┌────────────┐  ① 用户在网页上配置方案/点位/讲解词
│  前端网页   │
└─────┬──────┘
      │ HTTP
┌─────▼──────┐  ② 数据存在 JSON 文件里（plans.json / guides.json / maps.json）
│ Flask 后端  │     对外提供 /api/... 接口（本机 5000 端口）
└─────┬──────┘
      │ HTTP（urllib 请求 JSON）
┌─────▼─────────────────┐  ③ 讲解任务节点（本教程主角，Python 写的）
│ guide_mission_node    │     拿方案 → 循环：导航 → 播报
└───┬──────────────┬───┘
    │ Action 导航    │ Service 语音
┌───▼─────┐   ┌─────▼──────┐
│ Nav2 导航 │   │ voice 语音  │  ④ 语音节点负责：文字 → 语音合成 → 喇叭播放
│ 运动底盘  │   │  + 扬声器   │     （代码在本工作区 ros2/guide_voice 里，本教程只讲它的"接口"）
└─────────┘   └────────────┘
```

### 1.3 每个角色干什么

| 角色 | 在哪里 | 用什么写的 | 干什么 | 本教程讲吗 |
|---|---|---|---|---|
| 前端网页 | LY_speak_ws/web | Vue.js | 管理页面：配方案、点位、讲解词 | 不讲，第 5 章数据流里带过 |
| Flask 后端 | LY_speak_ws/backend | Python | 读写 JSON 数据、提供 API | 只讲用到的 4 个接口 |
| **讲解任务节点** | **ros2/ly_speak_mission** | **Python + rclpy** | **按方案逐点导航 + 播报** | ✅ 主角，全部讲 |
| Nav2 导航栈 | LY_inspect_ws | C++ | 接收目标点，控制底盘走过去 | 只讲怎么"用"它 |
| voice 语音服务 | ros2/guide_voice（本工作区） | Python | 文字合成语音并从喇叭播 | 只讲怎么"用"它 |

**关键心态**：讲解任务节点一行导航算法都没写、一行语音合成都没写。它只做三件事：**取数据 → 按顺序调用两个服务 → 处理各种失败情况**。真实的工程开发大部分是"调用 + 容错 + 编排"，不是造轮子。

## 2. 必懂概念速成

每个概念按「是什么 / 为什么 / 在本项目哪里出现」来讲。

### 2.1 ROS2 是什么

ROS2（Robot Operating System 2）= 机器人上的"通信框架"。它解决的问题：机器人的各个程序（导航、语音、传感器……）由不同人、不同语言写，怎么让它们互相说话？

本项目涉及的 5 个核心机制：

**① 节点 Node** —— 一个运行中的程序。类比：公司里的员工，有名字（如 guide_mission_node）。整个机器人系统 = 一群互相通信的节点。

**② 话题 Topic** —— 单向广播。类比：大喇叭，谁订阅谁听，说话的人不管有没有人听。本项目例子：`/guide_tts/status`（语音节点广播"播报状态"，任务节点订阅收听）。

**③ 服务 Service** —— 一问一答（请求/响应）。类比：打电话，问一句等一句回答。本项目例子：`/guide_voice/speak`（"请说这句话" → "好的，已排队"）、`/ly_speak_mission/start`（"开始任务" → "收到"）。

**④ 动作 Action** —— 长时间任务 + 可取消 + 可反馈进度。类比：请人送快递，可中途取消，对方可汇报"到哪了"。本项目例子：`/navigate_to_pose`（"走到 (x,y)"，导航要跑几十秒，一问一答覆盖不了）。

**⑤ 参数 Parameter** —— 节点启动时的"设置项"（键值对）。类比：命令行参数。本项目例子：`plan_id`、`dry_run`。启动时用 `--ros-args -p plan_id:=1` 覆盖默认值。

> 补充：节点之间靠"域名"互相发现，ROS_DOMAIN_ID 就是频道号——同频道的节点才能互相看见。这台机器人所有 ROS 程序都在频道 6，这就是代码里反复出现 `ROS_DOMAIN_ID=6` 的原因。

为什么用 ROS2 而不是自己写网络代码：通信、服务发现、跨语言、标准消息格式、调试工具（ros2 topic list 等）都是现成的。

### 2.2 工作区、包、colcon、source

- **包 package**：代码的最小组织单元，有 package.xml 的目录。类比 Python 的 pip 包。
- **工作区 workspace**：放多个包的目录，构建后多出一个 install/ 子目录。机器人上的工作区根 = `/home/smart/LY_speak_ws/ros2/`。
- **colcon build**：构建工具，把包"编译+安装"到 install/。Python 包没有真编译，主要做文件复制和生成启动器。
- **source install/setup.bash**：把一个工作区"激活"进当前终端——设置环境变量，让 `ros2 run` 找得到包、Python 找得到模块。**每个新终端都要重新 source**，这就是 start_mission.sh 开头一串 source 的原因。
- 类比：source = 把工具箱里的工具倒到桌面上，这个终端才认识它们。

### 2.5 HTTP 与 JSON

- **HTTP**：程序间传数据的协议。本项目里任务节点用 `http://127.0.0.1:5000/api/...` 向后端要数据——就是"浏览器敲网址拿内容"的自动化版。127.0.0.1 = 本机。
- **GET**：只读请求（查数据）。本项目只用了 GET。
- **JSON**：文本数据格式 `{"键": 值}`，跨语言通用。Python 用 `json.loads` 把 JSON 文本变成字典。
- **REST 接口**：用 URL 路径表示"要什么资源"，如 `/api/guide/byPlan/1` = "1 号方案的所有讲解点"。

## 4. 逐文件精讲

### 4.1 package.xml —— 包的身份证

```xml
<?xml version="1.0"?>
<?xml-model href="..." schematypens="..."?>
```
🧩 第 1-2 行：XML 声明和格式校验声明，**模板，永远不动**。XML 是一种标签式文本格式（像 HTML），`<a>内容</a>` 成对出现。

```xml
<package format="3">
```
🧩 根标签。format="3" 是 ROS2 包格式版本号，固定。

```xml
<name>ly_speak_mission</name>
<version>0.1.0</version>
<description>LY_Guide 讲解任务执行节点：...</description>
<maintainer email="smart@example.com">smart</maintainer>
<license>Apache-2.0</license>
```
🧩 元数据：包名（必须和目录名一致）、版本、描述、维护者、许可证（ROS 开源惯例 Apache-2.0）。

```xml
<exec_depend>rclpy</exec_depend>
<exec_depend>nav2_msgs</exec_depend>
<exec_depend>action_msgs</exec_depend>
<exec_depend>std_msgs</exec_depend>
<exec_depend>std_srvs</exec_depend>
<exec_depend>insp_interfaces</exec_depend>
```
🧩 **依赖清单**——这个包运行时 import 了哪些别的包（exec = execute，运行时依赖）。类比 Python 的 requirements.txt：
- `rclpy`：ROS2 的 Python 客户端库（所有 Python 节点都依赖它）
- `nav2_msgs`：Nav2 导航栈的消息定义（NavigateToPose 这个 Action 在这）
- `action_msgs`：Action 通用消息（GoalStatus 状态码在这）
- `std_msgs`：标准消息（String 字符串类型在这）
- `std_srvs`：标准服务（Trigger 服务类型在这）
- `insp_interfaces`：**你们项目的自定义接口包**（本工作区 ros2/insp_interfaces 自带一份），定义了 Speak 服务类型
- `<!-- ... -->` 是 XML 注释，说明 insp_interfaces 缺失时的兜底行为（见 4.6）

```xml
<export>
  <build_type>ament_python</build_type>
</export>
```
🧩 声明构建类型：纯 Python 包（ament_python）。模板固定。

### 4.2 setup.py / setup.cfg / resource/ —— 让包"可安装、可运行"

```python
from setuptools import setup
package_name = 'ly_speak_mission'
```
🐍 引入 Python 官方打包工具 setuptools；把包名存成变量。

```python
setup(
    name=package_name,
    version='0.1.0',
    packages=[package_name],
```
🧩 `packages=[package_name]`：声明"要打包的 Python 模块目录是 ly_speak_mission/ 这个文件夹"。
⚠️ 有两层同名目录：外层 `ly_speak_mission/` 是 **ROS 包目录**，内层 `ly_speak_mission/` 是 **Python 模块目录**，这是 ROS 惯例，容易绕晕，记住即可。

```python
    data_files=[
        ('share/ament_index/resource_index/packages', ['resource/' + package_name]),
        ('share/' + package_name, ['package.xml']),
    ],
```
🧩 **必须照抄的两行**：把 resource/ly_speak_mission 空文件和 package.xml 复制到安装目录指定位置。第一行是"注册"——装到 `share/ament_index/resource_index/packages/` 下，ROS 命令行工具（ros2 pkg list 等）才知道有这个包。**resource/ly_speak_mission 这个空文件的意义就是被复制过去当"登记牌"，内容永远为空。**

```python
    entry_points={
        'console_scripts': [
            'guide_mission_node = ly_speak_mission.guide_mission_node:main',
        ],
    },
```
🧩💡 **全文件最重要的两行**。意思：生成一个名叫 `guide_mission_node` 的可执行命令，运行时调用模块 `ly_speak_mission.guide_mission_node` 里的 `main` 函数。这就是 `ros2 run ly_speak_mission guide_mission_node` 能工作的原理：`ros2 run <包名> <可执行名>` → 找到命令 → 执行 → 跑到我们写的 main()。

setup.cfg：
```ini
[develop]
script_dir=$base/lib/ly_speak_mission
[install]
install_scripts=$base/lib/ly_speak_mission
```
🧩 colcon 的惯例配置：可执行脚本装到 lib/<包名>/ 下。照抄，不用深究。

### 4.3 start_mission.sh —— 一键启动脚本

```bash
#!/bin/bash
```
🐍(bash) shebang。

```bash
# 用法：bash start_mission.sh [ros2 run 参数...]
# 常用参数：--ros-args -p dry_run:=true -p plan_id:=1
# 注意：不能加 -u（nounset）——/opt/ros/humble/setup.bash 引用了未定义变量，严格模式下直接报 unbound variable
set -eo pipefail
```
💡 第 3 行注释告诉"未来的自己"怎么传参。第 5 行注释记录真实教训：曾经想加 `-u`（更严格的检查），结果 ROS 自带的 setup.bash 里有未定义变量，脚本直接报错。**注释里写"为什么不能这样做"，比写"做了什么"更值钱。**
第 6 行 `set -eo pipefail`：出错就停（见 2.4）。

```bash
SCRIPT_DIR=$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)
```
💡 经典一行：拿到"这个脚本自己所在目录"的绝对路径，不管你在哪个目录执行它都能找到同伴文件。拆开读：`${BASH_SOURCE[0]}` = 脚本自己的路径 → `dirname` = 去掉文件名留目录 → `cd` 进去 → `pwd` 打印绝对路径 → `$(...)` 把结果存给 SCRIPT_DIR。

```bash
export ROS_DOMAIN_ID="${ROS_DOMAIN_ID:-6}"
```
💡 **血泪教训写成的一行**。这台机器人所有 ROS 程序都在频道 6。曾经重启语音服务时漏了这行，语音落到频道 0，全机器人静音。`${ROS_DOMAIN_ID:-6}` = "你已设了就用你的，没设就默认 6"；export 让后面的 ros2 进程继承。

```bash
source /opt/ros/humble/setup.bash
source "${SCRIPT_DIR}/../install/setup.bash"
```
💡 两连 source（见 2.2"激活工作区"），**顺序不能乱：先系统、再自己**：
1. `/opt/ros/humble/setup.bash`：系统级 ROS2（humble = 发行版名字），让 `ros2` 命令存在；
2. 自己工作区的 install：让 `ros2 run` 找得到 ly_speak_mission 包——**语音服务的消息类型 insp_interfaces 也是本工作区自己构建的**（ros2/insp_interfaces）。

> 历史版本：这里曾经还有一行 `source /home/smart/LY_inspect_ws/install/local_setup.bash`（巡检栈工作区），因为当时的语音服务类型来自巡检。后来按需求把语音服务整个独立搬进了本工作区（ros2/guide_voice + ros2/insp_interfaces），这行就删掉了——**讲解任务不再依赖巡检工作区**。`2>/dev/null || true` 的写法含义：报错也不终止脚本（适用于"这个依赖不一定存在"的场景）。

```bash
exec ros2 run ly_speak_mission guide_mission_node "$@"
```

#### 第 4 段：服务回调与主循环（第 69-87 行）

```python
def _on_start(self, request, response):
    if self._busy:
        response.success = False
        response.message = "任务正在执行中"
    else:
        self._start_requested = True
        response.success = True
        response.message = "已受理，即将开始讲解任务"
    return response
```
💡 服务回调的固定签名：(请求, 响应) → 返回响应。逻辑：**正在忙就拒绝，空闲就受理**。注意它不直接执行任务，只置标志 `_start_requested = True`——因为回调里干重活会卡住整个节点，真正执行在主循环。**"回调只做轻活，重活放主循环"是 ROS 开发的铁律。**

```python
def run(self):
    while rclpy.ok():
        rclpy.spin_once(self, timeout_sec=0.1)
        if self._start_requested and not self._busy:
            self._start_requested = False
            self._run_mission()
```
💡 主循环（main 里调用它）。`rclpy.ok()`：节点还活着就循环。`spin_once`：**处理一次积压的 ROS 消息/回调**——ROS 节点不是魔法自动收发，必须"转起来"（spin）才处理通信。所以模式是：**转一下（处理通信）→ 看看有没有活 → 有活就干**。执行任务期间，spin 由 _sleep 和 _wait 继续做，不会完全卡死。

逐点讲解设计意图：

- **`self._busy = True` 开头、`finally` 里复位**：`try...finally` 保证"无论中间哪一步出错/提前 return，最后一定会执行 finally 里的解锁"——忘了解锁的话，一次失败后节点永远拒绝新任务（死锁）。
- **① 选方案**：就是"plan_id 怎么判断执行哪个任务"的逻辑（第 6 段细讲）。
- **②③④⑤ 每一步失败都有"说了原因 → return"**：失败时**用语音告知失败原因**（现场用户听到的是人话），这是面向真实用户的产品思维，不只是打日志。
- **⑥ 循环里 `continue`**：单个点位导航失败**不放弃整个任务**，跳下一个点继续——一个点失败好过整场讲解没了。
- **到达才播报**：`_navigate_to` 返回 True 才 `_speak_long(content)`，"到达即触发"是需求。
- ④⑤顺序：先检查导航（没有导航任务毫无意义），语音离线只警告——**依赖分轻重，处理方式不同**。

```python
def _http_get(self, path):
    url = self.get_parameter("backend_url").value.rstrip("/") + path
    try:
        with urllib.request.urlopen(url, timeout=10) as resp:
            return json.loads(resp.read().decode("utf-8"))
    except (urllib.error.URLError, OSError, ValueError) as exc:
        self.get_logger().error(f"接口请求失败 {url}: {exc}")
        return None
```
💡 所有接口请求的唯一入口。拆解：
- `rstrip("/")`：去掉地址末尾多余斜杠（防拼成 `//api`）
- `urlopen(url, timeout=10)`：发 GET 请求，10 秒没响应就放弃
- `with ... as resp`：用完自动关闭连接（Python 资源管理写法）
- `resp.read().decode("utf-8")`：读原始字节 → 按 UTF-8 解码成文本（中文必需）
- `json.loads(...)`：JSON 文本 → Python 字典
- `except (URLError, OSError, ValueError)`：**三种可能的失败一把抓**（网络不通/系统错/JSON 解析错），统一返回 None。调用方只判断"是不是 None"，不用关心具体哪种失败——这叫**错误收敛**，让调用方代码干净。

```python
def _sleep(self, sec):
    deadline = time.monotonic() + max(0.0, float(sec))
    while rclpy.ok() and time.monotonic() < deadline:
        rclpy.spin_once(self, timeout_sec=0.1)
```
💡 **用 spin_once 实现的 sleep**：为什么不用 `time.sleep`？因为 time.sleep 会让节点"睡死"，期间不收任何 ROS 消息（比如 /guide_tts/status 就收不到了）。这个 _sleep 一边计时一边处理通信，是 ROS 节点里"等待一段时间"的正确姿势。`time.monotonic()` 是单调时钟（不受系统改时间影响）。

#### navigate 核心（第 37-85 行）—— 一个 Action 的完整生命周期

组装目标（第 47-54 行）：

```python
goal = NavigateToPose.Goal()
goal.pose.header.frame_id = self._frame_id          # 坐标系：map = 地图世界坐标
goal.pose.header.stamp = self._node.get_clock().now().to_msg()   # 时间戳
```

📦💡 ROS 消息"填表"的标准流程：先 `Goal()` 建空消息，再往字段填值。两个知识点：
- **frame_id**：坐标相对哪个坐标系。map = 整张地图的统一坐标系。填错坐标系（比如填了机器人自身坐标系），坐标会差十万八千里。
- **四元数（quaternion）**：3D 旋转的标准表示法（4 个数），ROS 用 (x,y,z,w)。绕 Z 轴转 yaw 角时：x=y=0，z=sin(yaw/2)，w=cos(yaw/2)。**公式记不住没关系，知道"这四行就是把角度换算成 ROS 要的格式"就行。**

三步提交（第 56-78 行）—— **Action 通信的固定三拍**：

```python
send_future = self._client.send_goal_async(goal)   # 第1拍：发出目标
if not self._wait(send_future, 10.0):              # 等"发送"结果
    ...timeout
self._goal_handle = send_future.result()           # 拿到"目标受理单"
if ... not self._goal_handle.accepted:             # 导航可能拒收！
    return NavigationResult(False, "rejected", "goal rejected")

result_future = self._goal_handle.get_result_async()  # 第2拍：要最终结果
if not self._wait(result_future, timeout_sec):        # 等"走完"结果（可能120秒）
    self.cancel()                                     # 超时 → 主动取消
    ...
status = int(result_future.result().status)           # 第3拍：读状态码
if status == GoalStatus.STATUS_SUCCEEDED:             # 4 = 成功
    return NavigationResult(True, "succeeded")
if status == GoalStatus.STATUS_CANCELED:              # 5 = 被取消
    return NavigationResult(False, "canceled")
return NavigationResult(False, "failed", f"Nav2 status={status}")
```
📦💡 三个概念：
- **Future（未来）**：异步操作的"回执单"。发出请求后不能马上知道结果，先拿个 Future，之后问它"好了没/结果是什么"。**异步 = 不傻等**：等待期间 `_wait` 一直在 spin（处理其他通信），没卡死节点。
- **accepted（受理）**：Action 分两步——先"收不收单"，再"干活"。导航栈忙时会拒收，必须处理。
- **GoalStatus 状态码**：ROS 定义的标准数字（4=成功、5=取消、6=中止……）。我们把它翻译成自己定义的文本状态返回给导演。

#### _wait 辅助（第 99-103 行）

```python
def _wait(self, future, timeout_sec) -> bool:
    deadline = time.monotonic() + max(0.0, float(timeout_sec))
    while rclpy.ok() and not future.done() and time.monotonic() < deadline:
        rclpy.spin_once(self._node, timeout_sec=0.1)
    return future.done()
```
💡 **本文件最重要的一个模式**：等待 = 循环 spin + 查 future.done() + 看时间。以后你写任何"等 ROS 异步结果"都是这个模板。`future.done()` 由 ROS 框架在结果到达时置真。

### 4.6 voice_client.py —— 语音剧务

#### 双模式导入（第 19-24 行）

```python
try:
    from insp_interfaces.srv import Speak
    _HAS_INSP_INTERFACES = True
except ImportError:
    _HAS_INSP_INTERFACES = False
```
💡 **防御式设计**：Speak 服务类型定义在本工作区自带的 insp_interfaces 包里。如果哪天本工作区没 source，import 会抛 ImportError。这里抓住错误，切换到"命令行兜底模式"（用 `ros2 service call` 子进程调用）。**一条路径断了还有一条**——工程里叫"降级"。

#### 正则工具（第 26-28 行）

```python
_PUNCT_RE = re.compile(
    r"[\s，。！？；、,.!?;:：；（）()【】\[\]{}《》<>\"'‘’“”`·~～@#￥$%^&*_+=|\\/—-]+"
)
```
🐍 `re.compile` 把"模式"编译成可复用的匹配器。这个模式 = "一个或更多（+）的空白或标点字符"。用途：**把两句话去掉标点后比较是否相同**（判断"状态消息里说的这句"是不是"我发的那句"）。注意字符集里有中文标点（，。！？）——处理中文文本的正则必须显式列出中文标点。

#### 构造：订阅状态话题（第 34-43 行）

```python
self._status_sub = node.create_subscription(String, "/guide_tts/status", self._on_status, 10)
```
📦 创建订阅：`create_subscription(消息类型, 话题名, 回调, 队列长度)`。效果：语音节点每广播一条状态，框架自动调 `_on_status`。**这就是 2.1 里"话题"的用法**：单向收听，不打扰对方。

```python
self._lock = threading.Lock()
```
🐍 互斥锁：保证同一时刻只有一个线程改 `_last_status`（回调与等待循环可能并发访问）。`with self._lock:` 进入时拿锁、退出时还锁。

#### 说一句话的完整流程 speak → _speak_client（第 65-91 行）

```python
req = Speak.Request()
req.text = text
req.interrupt_current = False
started = time.monotonic()
future = self._client.call_async(req)
```
📦 服务调用四步：建请求 → 填字段 → 异步调用 → 拿 Future。`interrupt_current=False` 是**血泪教训**（见第 6 章坑史②）：False = "排队，等我上一条说完"，True = "打断当前正在说的话"。讲解任务必须排队不打断。

```python
while rclpy.ok():
    if future.done() or time.monotonic() - started >= 2.0:
        break
    rclpy.spin_once(self._node, timeout_sec=0.05)
self._wait_finished(text, started)
```
💡 等"受理"最多 2 秒（受理应该很快，久等没意义），然后进入**真正的等待——等播完**。

> 小瑕疵提示：CLI 兜底模式（_speak_cli）里 `interrupt_current` 写的是 True，和客户端模式不一致——因为兜底模式几乎不会被用到（机器人上 insp_interfaces 一直都在），所以一直没出事。**读代码时发现这种"历史遗留的不一致"很正常，这正是代码评审要找的东西。**

#### 等播完 _wait_finished（第 114-140 行）—— 三个判据缺一不可

```python
deadline = time.monotonic() + min(120.0, max(10.0, len(text) * 0.7 + 6.0))
```
💡 超时上限公式：**合成约 0.35 秒/字 + 播放约 0.25 秒/字 ≈ 0.7 秒/字**，加 6 秒余量；至少等 10 秒、最多 120 秒。为什么"宁可等满也不能提前超时"？**提前超时会让下一条播报打断还没说完的上一条**（坑史③）。

```python
completed = status.get("state") in {"end", "interrupted", "error"}
received_after_request = status.get("_recv_mono", 0) >= started
matching_text = _PUNCT_RE.sub("", str(status.get("text") or "")) == key
if completed and received_after_request and matching_text:
    ...return
```
💡 判定"我发的那句话播完了"需要**同时满足三条**：
1. **state 是终态**（end/interrupted/error）——语音节点播完会广播终态；
2. **这条状态是我发请求之后收到的**——防止旧状态冒充新结果（`_recv_mono` 是 _on_status 里盖的"收件时间戳"）；
3. **状态里的文本 = 我发的那句话**（去掉标点后逐字比较）——防止把别人（比如巡检语音服务）播报的结束误当成我的。
缺一条都可能误判。**写"等待完成"的代码，80% 的功力花在"证明完成的是我这件事"上。**

#### _on_status（第 142-150 行）

```python
def _on_status(self, msg: String):
    try:
        payload = json.loads(msg.data or "{}")
    except (TypeError, ValueError):
        return
    if isinstance(payload, dict):
        payload["_recv_mono"] = time.monotonic()
        with self._lock:
            self._last_status = payload
```
💡 话题回调：解析 JSON（坏数据直接忽略）、盖时间戳、加锁存起来。注意**回调里只做轻活**（解析+存），重判断都在 _wait_finished 里。

| | 导演 guide_mission_node | 剧务 navigation_client | 剧务 voice_client |
|---|---|---|---|
| 知道业务吗 | 知道（方案、点位、顺序、充电点） | 不知道，只懂"走到 (x,y)" | 不知道，只懂"说这句话" |

## 5. 一次任务的完整时间线（数据是怎么流的）

以 `bash start_mission.sh --ros-args -p plan_id:=1`（一楼展厅方案）为例，跟着数据走一遍：

1. 脚本 source 两个环境 → exec 启动节点；参数 plan_id:=1 被 rclpy.init 解析，覆盖默认值 0。
2. 节点构造：声明参数、创建服务、订阅 /guide_tts/status。auto_start=true → _start_requested 置真。
3. 主循环转起来 → 发现有请求 → _run_mission 上锁执行。
4. **_pick_plan**：GET /api/plan/1 → 后端查 plans.json，返回 `{"id":1,"planName":"一楼展厅地图 讲解方案",...}`。
5. **_fetch_points**：GET /api/guide/byPlan/1 → 返回 4 个讲解点（拆码垛展示区 → 技术迭代展示区 → 激光视觉展示区 → 焊接工件展示区），过滤 + 按 sort 排序；再 GET /api/map/1 拿充电点。
6. **_resolve_charge**：maps.json 里有 chargeX/chargeY 就用，否则兜底 (18.52, 1.0, -94)。
7. 确认导航在线 → 确认语音在线 → 说"开始讲解任务……"（voice_client → /guide_voice/speak → 语音节点合成 → 扬声器）。
8. **循环 4 次**：说"正在前往X号点位" → NavigationClient 发 NavigateToPose 目标（map 坐标系、四元数朝向）→ Nav2 规划路径驱动机器人 → 到达（status=4）→ 说讲解词（整段一次请求 → 等 /guide_tts/status 报 end）→ 下一个点。
9. 4 个点播完 → 说"返回充电点" → 导航到充电点 → 说"讲解结束" → finally 解锁 _busy。
10. 之后随时可 `ros2 service call /ly_speak_mission/start std_srvs/srv/Trigger "{}"` 再触发一遍。

## 6. 为什么这么写 —— 真实踩坑史（设计决策表）

好代码不是"写出来"的，是"改出来"的。这个包里的每个奇怪之处都对应一次真机事故：

| 代码里的样子 | 曾经的写法 | 出过的事 | 现在的设计 |
|---|---|---|---|
| `_speak_long` 整段一次发 | 按句号逐句发 /guide_voice/speak | 播报一顿一顿、每段开头吞字 | 整段一次请求，语音节点内部分块 |
| `req.interrupt_current = False` | True | 巡检播报和讲解互相打断、"说一个字就断" | 讲解排队不打断（True=抢占留给巡检） |
| 超时公式 len*0.7+6 | 固定 45 秒 | 长文本播到一半被下一句打断 | 按时长算上限，宁可等满不提前超时 |
| start_mission.sh 里 export ROS_DOMAIN_ID | 没有 | 重启语音漏设变量 → 落错频道 → 全静音 | 脚本强制默认频道 6 |
| _wait_finished 三条判据 | 只看 state | 旧状态/别人播报误判成"我播完了" | 终态 + 时间戳 + 文本三者匹配 |
| dry_run 参数 | 无 | 真机没导航环境时没法联调 | 虚拟到达开关 |
| 语音不在线 → 静音执行 | 直接终止 | 语音挂了整个讲解瘫痪 | 降级继续，只警告 |
| 单点导航失败 continue | 终止任务 | 一个点坏了整场讲解没了 | 跳过坏点继续 |
| CLI 兜底模式 | 只有 rclpy 客户端 | insp_interfaces 缺失直接崩 | import 失败自动降级 |
| _busy 标志 + try/finally | 无锁 | （防患于未然）并发触发互相打架 | 互斥 + 保证解锁 |
